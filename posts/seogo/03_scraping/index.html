    1. 소개

    Ray 를 활용한 병렬 스크래핑

    Ray를 사용해서, 스크래핑 시간을 단축하고 실제 DB를 구축해보자. 목표는 교보문고 전자책 DB를 구축하는 것이다. 이제 실전이다. 지난 번에 정리한 Task, Actor, Object 스토어를 어떻게 구성해야 스크래핑을 원활하게 할 수 있을까?



    2. Ray 스크래핑 구조

    2-1. Actor 역할 분리

    우선 줄글로 정리하면

    웹에서 데이터를 파싱받아와서, DB안에 집어넣어야함 그래서 두종류의 Actor가 필요

    1. Driver (지휘자)

    • 사용자가 실행하는 메인 파이썬 스크립트(main.py)이다.
    • 모든 for 루프(반복문)의 유일한 소유자이다. 즉, 도서관-테마-페이지 계층 구조를 탐색하고 낱개의 URL을 생성하는 모든 로직을 담당한다.
    • Actor를 생성하고, 작업(Task)을 예약(remote())하며, 전체 흐름을 제어한다.

    2. Scraping Actor (일꾼)

    • @ray.remote 클래스로 정의되며, **독립된 프로세스(Process)**로 실행된다.
    • 1 Actor = 1 Browser 원칙에 따라, __init__(초기화) 시점에 브라우저(Playwright/Selenium)를 1회 실행하여 내부 상태(State)로 소유한다.
    • 내부에는 반복문이 존재하지 않는다. scrape_url(url, ...)처럼 URL 1개만 받아 처리하는 단순한 메서드만 가진다.
    • 브라우저를 재사용함으로써 매번 켰다 끄는 오버헤드를 제거한다.

    3. Database Actor (창고지기)

    • 단일 인스턴스(Singleton)로 생성되는 @ray.remote 클래스이다.
    • DB 연결(Connection)을 독점적으로 소유하고 관리한다.
    • 수십 개의 Scraping Actor로부터 동시에 쏟아지는 저장 요청(save.remote(data))을 내부 작업 큐(Queue)에 따라 순차적으로(Serially) 처리한다.
    • 이는 DB 커넥션 폭증을 막고, 데이터베이스를 안전하게 보호한다.

    2-2. 작업 흐름 및 병렬화 전략

    효율적인 병렬 처리를 위한 작업 흐름은 다음과 같다.

    1. 작업 평탄화 (Flattening)

    • Scraping Actor에게 ‘URL 리스트(List)‘를 통째로 넘기지 않는다. 이는 심각한 작업 불균형(Load Imbalance)을 초래한다. (어떤 Actor는 10페이지, 어떤 Actor는 5000페이지를 받아 불공평하게 일함)
    • Driver가 for 루프를 돌며 **‘낱개 URL’**을 생성한다.

    2. 즉시 전송 및 선착순 처리

    • Driver는 낱개 URL이 생성되는 즉시 worker.scrape.remote(url, ...)를 호출하여 Ray의 중앙 작업 대기열(Scheduler Queue)에 등록한다.
    • remote() 호출은 비동기적(Non-blocking)이므로 Driver의 for 루프는 멈추지 않고 순식간에 수만 개의 작업을 예약한다.
    • Scraping Actor들은 이 대기열에서 선착순으로 작업(URL)을 하나씩 가져가 처리한다.
    • 이 방식은 특정 Actor가 놀지 않고 모든 자원이 공평하게 일하도록 보장한다.

    3. 비동기 저장 (Fire-and-Forget)

    • Scraping Actor는 데이터 수집 후, db_actor.save.remote(data)를 호출하고 ray.get()으로 기다리지 않는다.
    • 저장이 완료될 때까지 기다리지 않고(Fire-and-Forget), 즉시 다음 작업을 받으러 가므로 스크래핑 효율이 극대화된다.

    2-4. 리소스 관리 및 오버헤드

    시스템 자원을 효율적으로 사용하기 위한 전략이다.

    1. Actor 풀 크기 결정

    • 스크래핑은 네트워크 응답을 기다리는 I/O-Bound(대기 집약적) 작업이다.
    • 따라서 Actor의 개수는 CPU 코어 수보다 훨씬 많아야 한다.
    • Actor(브라우저)가 I/O 대기로 인해 CPU를 사용하지 않을 때, Ray와 OS는 다른 Actor를 즉시 CPU에 할당(Context Switching)하여 CPU 효율을 100%로 유지한다.
    • Actor 개수의 한계는 CPU가 아니라 RAM이다. (Actor 개수 X 브라우저 1개당 RAM 사용량)이 시스템의 총 가용 RAM을 넘지 않도록 설정해야 한다.

    2. Actor 내부 순차성

    • Actor는 기본적으로 단일 스레드로 동작한다.
    • 이는 여러 Task가 Actor의 상태(브라우저)에 동시에 접근하려 할 때 발생하는 충돌을 원천적으로 방지한다. Actor는 자신에게 온 작업 요청을 순차적으로 처리하며 브라우저의 안정성을 보장한다.

    5. 안정성 및 오류 처리 (체크포인트)

    수십만 건의 작업을 중단 없이 처리하기 위한 안정화 전략이다.

    1. 작업 단위(Batch) 선정

    • 19만 건의 작업을 단일 배치로 처리하는 것은 위험하다. (중간 실패 시 전체 재시작)
    • ‘도서관’ 단위는 너무 크고, ‘페이지’ 단위는 너무 작다.
    • ‘테마’ 단위(약 2~3만 건)가 체크포인트(Checkpoint)를 위한 가장 이상적인 작업 단위이다.

    2. 체크포인트 구현

    • Driver는 도서관 -> 테마의 2중 루프를 돈다.
    • 하나의 ‘테마’에 속한 모든 페이지 Task를 예약한 직후, ray.get()을 호출하여 해당 테마가 끝날 때까지 동기적으로 대기한다.
    • ray.get()이 예외 없이 성공적으로 완료되면, Driver는 completed_themes.txt와 같은 로그 파일에 lib_A::theme_001과 같이 완료된 작업 단위를 기록한다.
    • 스크립트 재시작 시, Driver는 이 체크포인트 파일을 먼저 읽어 이미 완료된 테마를 건너뛴다(Skip).
    • 이로써 작업이 중단되더라도 항상 마지막으로 성공한 테마 다음부터 이어할 수 있다.
