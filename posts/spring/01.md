springboot


Bean이란?
스프링이 생명주기를 관리하는 자바 객체
일반적으로는 new Apple(); 처럼 직접 생성해서 사용하느 객체
Bean은 우리가 직접 new 하지 않고 Spring 에게 이것좀 대신 만들어서 가지고 있어줘라고 맡기는것
이렇게 spring이 관리하는 bean들은 spring 이라는 거대한 바구니 안에 담겨 필요할때마다 꺼내쓰임

IoC 제어의 역전 컨테이너
우리는 만든 빈을 IoC 컨테이너에 담는다(바구니)
왜 제어의 역전인가? 원래 객체의 생성과 연결은 개발자가 직접 코드로 제어했다. 하지만 Spring에서는 이 주도권을 Spring 프레임워크가 가져감. 이걸 바로 제어의 역전이라고 함.
컨테이너는 Bean을 생성하고, 서로 연결해주고, 프로그램이 끝날때 소멸시키는 모든 과정을 책임짐.

DI 의존성 주입 -> 빈을 연결하는 방법
Bean들끼리 서로 협력해야할때, 컨테이너가 중간에서 연결해주는 것을 DI라고 한다.
예를 들어 Chef 라는 빈이 Knife라는 빈을 필요로 할때
- 개발자는 Chef는 Knife가 필요해 라고 설정만 해둔다.
- Spring 컨테이너가 실행될때 Knife 빈을 먼저 만들고, 그것을 chef 빈을 만들면서 슥 넣어줌.

@Configuration 클래스
이 어노테이션이 붙은 클래스는
"어떤 객체를 어떻게 만들어서 컨테이너에 넣을 것인가"를 결정하는 역할을 한다.
1. Spring boot 시작 시 @Confiuration이 붙은 클래스를 모두 찾아낸다
2. 그리고 그 안에 @Bean이 뭍은 메서드를 리스트업 한다.
3. 각 메서드를 미리 다 만들어서 바구니에 넣어둔다.

MVC와 템플릿 엔진
html을 그냥주는게 아니라 서버에서 프로그래밍해서 html을 동적으로 바꿔서 줌.

``` java
@GetMapping("hell-mvc")
public String hellMvc(@RequestParam("name") String name, Model model) {
    model.addAttribute("name", name);
    return "hello-template";
}
```
C++로 IRC 서버를 만드실 때, 클라이언트가 보낸 메시지 버퍼를 파싱해서 "이건 NICK 명령어구나", "이건 PRIVMSG구나"라고 판단한 뒤 그 안에 담긴 인자(Argument)를 추출했던 기억이 나실 겁니다. 스프링의 hellMvc 메서드는 바로 그 **'특정 요청을 받아서 인자를 파싱하고 응답을 준비하는 과정'**을 아주 세련되게 추상화해 놓은 것입니다. 하나씩 뜯어볼게요.

`@GetMapping`
- 웹브라우저가 http://localhost:8080/hell-mvc 라는 주소로 접근하면 "이 메서드를 실행해!"라고 지정하는 이정표

`@RequestParam("name") String name`
- Url 뒤에 붙는 쿼리 파라미터를 받아옴
- 주소가 `.../hell-mvc?name=steve` 라면 name 변수에 steve를 자동으로 할당
- c++ 관점에서 보면 소켓으로 들어온 문자열에서 ?name=spring 부분을 파싱하여 char *name에 담는 과정임
- 이 과정을 스프링에서는 @RequestParam("name") 이라는 어노테이션을 보고, 스프링 내부의 Dispatcher Servlet라는 놈이 다음과정을 수행
    - 들어온 http 요청 url을 확인
    - ?name=xxx 가 있는지 검사
    - 있다면 xxx라는 값을 꺼내서, hellMvc 함수를 실행할때 첫번째 인자로 넣어줌.

`Model model`
- 컨트롤러에서 처리한 결과물을 View로 전달하기 위한 매개체
- 그런데 이 함수 호출할때 인자를 내가 안 넣는데, 이 model 객체는 누가 생성해서 넣어주나?
- 이 함수를 호출하는 주체는 내가 아니라 Spring 프레임워크임.
- 스프링은 hellMvc의 파라미터 리스트를 쓱 흝어본다. 아 이 개발자가 데이터를 담은 Model 객체가 필요하구나? 라고 판단하고 본인이 관리하던 model을 주입해준다.


`model.addAttribute("name", name)`
- model 이라는 키로 위에서 받은 실제 값을 담는다. 나중에 html 템플릿에서 이 키 이름을 보고 값을 꺼내쓴다.

`return "hello-template`
- 스프링에게 결과물은 `resources/templates/hello-template.html` 파일을 찾아서 그려줘 라고 말하는 것.

### 제어의 역전

#### 호출을 내가 안한다고?
c++에서는 아래처럼 했었음
``` c++
if (command == "NICK") {
    handle_nick(client_socket, args);
}
```

그런데 스르핑에서는 Reflection이라는 기술을 사용한다.
1. 스프링이 실행되면서 전체 프로젝트를 탐색
2. @Controller가 붙은 클래스를 찾아서 메모리에 올림
3. 그 안에서 @GetMapping("hell-mvc")가 붙은 메서드를 찾아 Url 주소와 이 함수 포인터를 매핑한 테이블을 만듦
4. 사용자가 접속하면 DispatcherServelt이라는 거대한 메인 루프가 이 테이블을 보고 hellMvc를 대신 호출함

### Model의 정체
Model은 내부적으로 사실 Map 형태의 자료구조임.
- 왜 필요함?
    - 컨트롤러(C)와 화면(V)는 서로 남남. 자바코드(컨트롤러)에서 계산한 결과물을 HTML(화면)에게 전달해야하는데, 함수 리턴값은 보통 어떤 화면으로 갈지(파일이름)를 정하는데 사용함
    - 그래서 스프링이 데이터를 담을 공간을 하나 만들어서 컨트롤러에게 빌려줌.
    - 즉, 모델에는 컨트롤러의 결과값이 담기게 됨.

- c++ 처럼 생각해보자면?
    - 메인루프가 hellMvc를 호출하기 전에 빈 std::map (Model)을 하나 생성 -> 약간 std::map<std::string, void*> 와 비슷
    - 이 맵을 hellMvc(..., model)의 인자로 넘겨줌
    - 함수가 끝나고 hello-template(화면이름)을 리턴하면, 스프링은 그 map을 들고 HTML 렌더링 엔진 으로 달려감
    - 렌더링 엔진은 HTML파일 내의 ${name} 과 같은 태그를 발견하면 전달받은 map에서 name키로 값을 꺼내서 html 글자를 갈아끼움

- 왜 인자값을 이렇게 복잡하게 넣어주는거임? 그냥 전역변수 쓰거나 직접 객체 생성하지 않는 이유가?
    - 멀티스레드에서 안전성
        - 스프링은 각 요청(thread)마다 독립적인 Model 객체를 만들어서 주입해주기 때문에 안전
    - 결합도 낮추기
        - 내가 만약 직접 new model 하면, 나중에 화면 렌더링 방식 바꿀때 코드 다 고쳐야하니까 그냥 스프링이 넣어주는것을 받아서쓰면 내부 구현이 어떻게 바뀌든 내 로직은 안전.

- 그럼 model의 유효 범위 또는 유효한 생명주기는 어떻게 됨?
    1. 탄생: 우선 소켓에 패킷이 들어오면 DispathcerServlet(메인루프)가 "이 요청은 hellMvc가 처리해야겠네!"라고 결정하는 순간 Model 객체를 힙 메모리에 새로 생성함
    2. 유통: 생성된 model rorcprk hellMvc 함수의 인자로 전달됨->개발자가 여기에 데이터를 열심히 담음
    3. 전달 및 렌더링: spring은 이 모델 객체를 들고 뷰로 이동후 모델 안의 데이터를 꺼내서 html을 완성함
    4. 소멸: 완성된 html이 소켓을 통해 사용자 브라우저로 전송 -> 응답이 나가는 순간 스프링은 이 model 객체 참조 해제하며 곧 GC에 의해 메모리에서 사라짐. 
    5. 재사용X: 사용자가 새로고침을 하면 그것은 곧 새로운 요청이므로 새로운 model이 탄생함. 이전 모델에 담았던 데이터는 이미 사라지고 없음. 여러 페이지 이동중에도 데이터를 유지하고싶다면 다른 방법(db나 세션)을 사용해야함

- 그럼 model에는 주로 어떤 내용이 담겨서 유통됨?
    - 단순 정보(가장 기본적으로 화면에 뿌려줄 텍스트나 숫자)
    - DTO
    - 목록데이터(게시판의 글 목록이나 상품 목록 등)
    - UI 상태 제어값 등

- 요약하면 Model 이란
    - 컨트롤러가 작업한 결과물을 View(화면)라는 목적지까지 배달하기 위해 사용하는 범용적인 데이터 Map


## API

``` java
@GetMapping("hello-string")
@ResponseBody
public String helloString(@RequestParam("name") String name) {
    return "Hello " + name;
}
```

@ResponseBody: html 파일 찾지마.
- 이게 없었던 직전에는 함수가 hello를 리턴하면 스프링은 resources/templates/hello.html을 찾으러감
- 이 리턴값(string)은 파일이름이 아니야. 그냥 이 문자열 자체를 http 응답 패킷의 바디에 바로 때려박아줘
