## 📥 스프링 부트 요청 인풋(Input) 유형 총정리

HTTP 요청의 어느 부분에 데이터가 담겨 오느냐에 따라 크게 5가지로 나뉩니다.

### 1. 요청 데이터 분류 체계

| 구분 | 위치 | 설명 | 핵심 어노테이션 |
| --- | --- | --- | --- |
| **URL 경로 (Path)** | `/users/{id}` | URL 경로 자체에 값을 포함 (자원 식별) | `@PathVariable` |
| **쿼리 파라미터 (Query)** | `?name=kim&age=20` | URL 끝에 `?`와 함께 전달 (필터링, 검색) | `@RequestParam` |
| **폼 데이터 (Form)** | Body (`key=value`) | HTML `<form>` 태그를 통해 전달되는 데이터 | `@ModelAttribute` / `@RequestParam` |
| **메시지 바디 (API/JSON)** | Body (`{...}`) | REST API에서 주로 쓰는 JSON 형태의 데이터 | `@RequestBody` |
| **메타데이터 (Metadata)** | Header / Cookie | 인증 토큰, 브라우저 정보, 세션 ID 등 | `@RequestHeader` / `@CookieValue` |

---

## 2. 인풋별 상세 설명 및 활용

### 📍 URL 경로 변수 (`@PathVariable`)

* **특징:** 자원의 위치를 명확히 할 때 사용합니다.
* **예시:** `GET /posts/10` → 10번 게시글을 가져올 때.
* **용도:** 주로 RESTful API에서 특정 리소스를 식별하는 ID 값으로 씁니다.

### 🔍 쿼리 파라미터 (`@RequestParam`)

* **특징:** URL은 유지하면서 추가적인 옵션을 줄 때 사용합니다.
* **예시:** `GET /posts?category=tech&sort=desc` → tech 카테고리 글을 최신순으로 정렬할 때.
* **용도:** 검색, 필터링, 페이징 처리에 적합합니다.

### 📝 폼(Form) 데이터 (`@ModelAttribute`)

* **특징:** `application/x-www-form-urlencoded` 형식으로 전달됩니다.
* **용도:** 전통적인 웹 페이지의 회원가입, 게시글 작성 화면에서 사용자가 입력한 값을 객체(DTO)로 통째로 바인딩할 때 매우 편리합니다.

### 🤖 메시지 바디 / API (`@RequestBody`)

* **특징:** 주로 **JSON** 형식을 사용하며, 외부에 노출되지 않도록 HTTP Body에 담겨 옵니다.
* **용도:** 현대적인 웹(React, Vue)이나 앱과의 통신에서 복잡한 객체 데이터를 주고받을 때 표준으로 사용됩니다.

### 📑 메타데이터 (`@RequestHeader`)

* **특징:** 비즈니스 데이터가 아닌, 통신에 필요한 부가 정보를 담습니다.
* **용도:** 인증 토큰(JWT), 클라이언트 기기 정보(User-Agent), 응답받고 싶은 데이터 형식(Accept) 등을 확인할 때 씁니다.

## 🏗️ @Autowired 필드 주입을 사용하는 상황

### 1. 테스트 코드 (`@SpringBootTest`)

가장 대표적인 경우입니다. 테스트 코드에서는 객체의 불변성을 보장하거나 생성자를 복잡하게 설계할 필요가 없습니다.

* **이유:** 테스트 클래스는 스프링이 생성자를 통해 빈을 주입하는 방식과 JUnit의 동작 방식이 충돌할 수 있어, 가장 단순한 `@Autowired` 필드 주입을 주로 사용합니다.
* **예시:**
```java
@SpringBootTest
class MyTest {
    @Autowired
    MyService myService; // 테스트에서는 간결함이 최고!
}

```



### 2. 레거시 코드 유지보수

이미 수만 줄의 코드가 필드 주입 방식으로 작성된 프로젝트를 맡게 되었을 때입니다.

* **이유:** 혼자만 생성자 주입으로 바꾸면 코드의 일관성이 깨지고, 전체를 다 바꾸기엔 리스크가 큽니다. 이런 경우 팀의 컨벤션을 따르기 위해 계속 사용하기도 합니다.

### 3. 설정 클래스 (`@Configuration`)

스프링 설정 자체를 담당하는 클래스 내에서 다른 빈을 잠시 참조해야 할 때 사용합니다.

* **이유:** 설정 클래스는 실제 비즈니스 로직이 아니므로 불변성이나 테스트 용이성에서 상대적으로 자유롭기 때문입니다.

### 4. 의존성이 필수가 아닐 때 (Optional Dependency)

특정 빈이 없어도 프로그램이 돌아가야 하는 경우에 사용합니다.

* **방법:** `@Autowired(required = false)` 옵션을 주면, 주입할 빈이 없어도 에러가 나지 않고 `null`로 유지됩니다.
* **참고:** 생성자 주입은 빈이 없으면 객체 생성 자체가 안 되어 애플리케이션이 멈추기 때문에, 옵션이 필요한 경우 필드 주입이나 Setter 주입이 대안이 됩니다.

---

## ⚠️ 그럼에도 주의할 점

제공해주신 표를 보면 `@Autowired`는 **필드, 생성자, 메서드** 어디든 사용 가능하다고 되어 있습니다. 하지만 실무에서는 다음과 같은 이유로 여전히 생성자 주입을 선호합니다.

| 문제점 | 필드 주입 (`@Autowired`) | 해결책 (생성자 주입) |
| --- | --- | --- |
| **NPE 위험** | 주입 없이 객체를 생성하면 메서드 호출 시 터짐 | 객체 생성 시점에 주입이 강제됨 |
| **의존성 숨김** | 클래스 외부에서 어떤 의존성이 있는지 알기 어려움 | 생성자의 파라미터를 통해 명확히 보임 |
